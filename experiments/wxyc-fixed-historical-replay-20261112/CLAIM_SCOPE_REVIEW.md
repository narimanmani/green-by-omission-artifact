## What a qualifying positive observation could establish

The proposed case could demonstrate the following joint observation in one local, pinned upstream project:

1. The unchanged original unit-test oracle passes at the fixed baseline.
2. Native Jest selection actually executes at least one original test call, all selected calls pass, and the process succeeds without an infrastructure/observer error.
3. Independent execution of the complete original unit-test oracle on identical candidate bytes fails the original cookie-configuration source-policy assertion that selective execution omitted.
4. Test/configuration/dependency bytes, Git comparison base, candidate identity, selected/full test identities, original skips, and execution records match the declared protocol.

The detecting assertion is an original upstream security-configuration source guard: it rejects a hardcoded SameSite value in authentication source. It was committed with public fix `8e2fc5f320633ddec0e99e05b65b21682ed3ccda` and remains unchanged at the frozen later baseline. Its security purpose is explicit, but its observed predicate is lexical source policy.

If all conditions hold, this closes the **minimal original-test plus nonempty-execution conjunction for that source-policy assertion in native Jest**. It also meets the manuscript's general observable-violation definition at the designated-assertion level: the oracle exists, remains unchanged, fails on the candidate, and is absent from a nonempty passing selection. This would supply a genuinely joint observation, rather than combining Validator's empty original-test result with a separate research-authored nonempty result.

This would be one fixed case, with technical repetitions establishing reproducibility rather than independent discoveries or a success rate. Full oracle means the project's original unit-test scope defined by `jest.unit.config.ts`, not all integration/end-to-end tests or a deployed project.

## What it could not establish

- **Fingerprint-mechanism gap:** The paper's principal question concerns fixed-baseline fingerprint-preserving omissions in testmon/Ekstazi. Jest's Git/module-dependency selection provides a different dependency-observability case. No CRC32 equality, fingerprint collision, fingerprint-preservation construction, or failure of a stronger digest is established.
- **Original behavioral security oracle:** A source regex failure is not an observed HTTP/browser/authentication execution failure. It establishes breach of the original configuration guard, not runtime CSRF vulnerability, exploitability, or behaviorally demonstrated compromise. The stronger conjunction involving an unchanged original runtime security assertion remains open.
- **Authentic historical pair:** This is a controlled historical-fix reversion on a later passing baseline. The guard was added with the fix; it did not already exist in the authentic pre-fix revision. The case is not a discovered naturally occurring vulnerable revision pair, production incident, or measured prevalence result.
- **Hosted attacker-model validity:** A local Docker run supplies no new separate-contributor, protected-main/cache-producer, required-status, review, or merge evidence. It cannot expand the existing hosted result beyond its exact fixed-fixture policy, shared operator, distinct account permissions, separately required review and unmerged PR.
- **Arbitrary-contributor feasibility:** One frozen public-fix reversion supplies no candidate-discovery rate, search budget, arbitrary source-code admission guarantee, or bypass of an independently required complete-oracle job.
- **General mitigation effectiveness:** A positive native omission would not evaluate a new defense, demonstrate universal unsafety, or estimate deployment exposure. The public upstream CI subsequently moved to full-unit execution; the pinned historical configuration is the evaluated configuration.

The independent-selector arm already separates dependency-analysis omissions from replication of the fingerprint mechanism. This case belongs to that distinction. It would be a security-relevant, original-oracle illustration of documented dependency incompleteness, not a third implementation of the paper's fingerprint-preservation mechanism.
